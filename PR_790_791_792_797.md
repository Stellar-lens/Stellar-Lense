## Summary

This PR addresses four related gaps around irreversible score deletion, operator auditability, policy-boundary coverage, and consumer-facing exploit simulations.

### #791 — deletion preflight

Adds a read-only `get_deletion_preflight(wallet, asset_pair)` query so operators can inspect what a destructive deletion would affect before executing it.

Returned fields:

- `wallet`
- `asset_pair`
- `latest_score_present`
- `history_count`
- `audit_warning = Irreversible`

### #792 — stronger audit trails for irreversible deletion

Upgrades `clear_score` and `clear_score_history` audit events to include:

- reason hash
- category hash
- authorization context
- latest-score presence
- history count

Raw deleted score content is still excluded.

To preserve backward compatibility, existing delete entrypoints remain available and emit deterministic default hashes. New explicit variants were added for operators that want case-specific audit hashes:

- `clear_score_with_audit(...)`
- `clear_score_history_with_audit(...)`

### #797 — sandwich simulations around score updates

Adds deterministic composability simulations covering consumer queries immediately before and after suspicious score changes.

The simulations show:

- fail-closed behavior blocks consumers before a first score exists and again after the score is cleared
- cooldown prevents immediate score oscillation after a suspicious low-risk update, bounding the flip window

### #790 — policy boundary interactions

Adds focused tests covering boundary interactions between:

- cooldown + epoch
- confidence floor + score floor
- pause + override
- batch size + TTL/resubmit behavior

## Pre-change behavior documented

Before this PR:

- `clear_score` removed only the latest score entry
- `clear_score_history` removed only the history ring
- both were admin-only and no-op on missing data
- both updated histogram state only from the current latest score if one existed
- `clr_scr` / `clr_hist` emitted minimal events with no reason/category hash or auth context

This behavior is now documented in `docs/privacy-model.md`.

## Implementation details

Contract changes:

- added `DeletionAuditWarning` and `DeletionPreflight` contract types
- added `storage::peek_score_history_len(...)` to inspect history size without extending TTL
- added `get_deletion_preflight(...)`
- preserved `clear_score(...)` and `clear_score_history(...)` as compatibility entrypoints
- added `clear_score_with_audit(...)` and `clear_score_history_with_audit(...)`
- expanded `clr_scr` / `clr_hist` event payloads append-only while keeping topics unchanged
- included deletion authorization context in emitted events:
  - configured admin address
  - whether admin multisig was active
  - signer count supplied
  - required threshold

Tests added:

- deletion preflight success path
- deletion preflight empty boundary
- default audited `clear_score` event emission
- custom audited `clear_score_history` event emission with multisig context
- insufficient-admin-signers adversarial failure mode for audited delete
- cooldown + epoch interaction
- pause + override interaction
- confidence floor + score floor interaction
- batch-size + TTL/resubmit boundary
- sandwich simulations for AMM/lending consumers around suspicious score changes

## Compatibility impact

- Public ABI: additive only
  - existing delete entrypoints remain unchanged
  - new preflight and `*_with_audit` entrypoints are optional additions
- Event topics: unchanged
- Event payloads: append-only expansion for `clr_scr` and `clr_hist`
- Errors: unchanged
- Storage layout: unchanged
  - no new persistent deletion log is stored

## Resource bounds

- `history_count` is derived from the bounded score-history ring, still capped by `MAX_HISTORY_DEPTH = 50`
- batch-related coverage remains bounded by `MAX_BATCH_SIZE = 20`
- no unbounded iteration was added to the new deletion-preflight path
